# Forge Design OS

## Prime directive
Work from the product, not from a blank canvas. Read the brief, existing UI, components, tokens, data, workflows, and constraints before changing anything. Existing product constraints outrank generic design advice.

## Required loop
CONSTRAINTS → EXPLORE → REDUCE → PROTOTYPE → TEST WITH DATA → CRITIQUE → SHIP → CAPTURE

### 1. Constraints
Define the whole system before implementation: user, job, workflow, information hierarchy, existing design language, technical constraints, accessibility, mobile behaviour, data states, and what must not change.

### 2. Explore
For meaningful design work, consider at least three materially different solutions before selecting one. Do not create three cosmetic variants of the same idea.

### 3. Reduce
Run a subtraction pass. Ask of every element: does this help the user understand, decide, or act? Remove decoration, duplicate explanation, unnecessary cards, excessive gradients, badges, icons, and UI chrome.

### 4. Prototype
Use existing components and tokens first. Add a new pattern only when the existing system cannot solve the problem cleanly. Avoid novelty for its own sake.

### 5. Test with data
Use realistic practitioner data, long labels, empty states, errors, loading states, mobile widths, and edge cases. Never approve a component using only ideal placeholder content.

### 6. Critique
Review the whole screen and workflow, not isolated pixels. Check hierarchy, comprehension, interaction cost, consistency, accessibility, and whether the design feels like Forge rather than generic AI SaaS.

### 7. Ship
Prefer the smallest coherent change that materially improves the product. Do not create redesign gravity when refinement is enough.

### 8. Capture
Record reusable patterns, decisions, tokens, and lessons so future work compounds.

## Anti-slop rules
- Clarity over cleverness.
- Familiar interaction conventions over novelty.
- Product objects and practitioner workflows should drive the interface.
- Do not solve local design problems by adding global complexity.
- Do not redesign unrelated areas while completing a scoped task.
- Avoid repetitive card grids when hierarchy or progressive disclosure is better.
- Typography, spacing, contrast, and content hierarchy come before decoration.
- Forge should feel calm, credible, evidence-led, and useful to a working sport leader.

## External expertise
When available, use specialist external skills for React/Next.js implementation, web design/accessibility review, and browser testing. They advise on craft. This Forge skill owns product intent and takes precedence where guidance conflicts.
